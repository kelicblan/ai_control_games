# 游戏前端性能审计与优化顺序

日期：2026-10-15。范围：桌面游戏页面、Three.js 渲染、状态同步、资源与界面。此次为审计，未修改游戏实现或玩家存档。

## 证据边界

- 已检查当前帧循环、地图、地形分块、角色动画、天气、网络快照和实际 GLB 文件。
- 本地 5173、18081 端口正在监听；浏览器诊断桥接失败，备用页面检查超时，因此没有取得本次浏览器 FPS、GPU 时间、长任务或截图。
- `validation-performance.md` 的 39–48 FPS 等是旧场景记录，不代表当前版本。旧测试页在主线程每 100ms 推进独立模拟，且 onProject 为空，不覆盖真实网络同步和 DOM 标签开销，不能替代实际游戏验收。
- 以下代码行为可确认；其占当前卡顿的比例仍需实际页面分阶段计时。不要把所有候选问题都当成已测根因。

## 本机辅助测量

使用项目 tsx 在 Node 中调用实际 sampleCampSurface，在营地中心周围 512 单位范围连续采样 128×128 点，六轮耗时为 223.84、39.43、39.58、33.90、36.65、40.05ms。

这是同规模全采样的 CPU 风险探针，不是小地图实测：真实小地图会跳过未知区域，并有其他采样与绘制工作；浏览器 JIT、设备占用也不同。不能将该数字直接当作页面帧耗时或优化收益。

三维距离逻辑复核：水平只移动 0.1、高度为 5 时，现有 distance 得到 5.001，超过 4，触发直接跳位。初始营地中心高度约 -0.045，故此问题有地形条件，不能单独解释所有平地卡顿。

## 实施顺序与验收

1. 为实际页面加入低开销的可关闭采样：帧间隔 P50/P95/P99、>50ms 帧数、各阶段 CPU 时间、draw calls/三角面、阴影更新帧标记、地块创建/释放、缓存命中率、快照大小与解析耗时。GPU 计时仅在扩展可用时启用，不把 renderer.render 的 CPU 调用时间当 GPU 耗时。
2. 第一批修水平插值、探索全量失效、小地图重采样，分别做可切换 A/B，确认尖峰来源。
3. 第二批处理相机/地形调度、天气查询、阴影和离屏表现更新。
4. 第三批拆分网络快照和 HUD 订阅；预处理资产、纹理与加载预算。

测试使用桌面实际游戏页面与生产构建，在同一设备/窗口/DPR/存档/视角路径下比较。覆盖上帝远景、领主原地/行走、寨门/房屋附近、晴天/暴雨/转风、NPC 揭雾、小地图展开、冷启动，以及持续运行 10–15 分钟。固定测试世界与真实页面都要测，避免独立预览的模拟开销或缺少 UI 导致结论失真。

建议验收目标（不是当前成绩）：常用桌面视角向 60 FPS 收敛；P95 帧间隔≤20ms、P99≤33ms；预热后不持续出现>50ms 长帧；若设备只能支撑 30 FPS，稳定在约33ms优于频繁波动。记录设备与画质后确定最终门槛。世界持续运行、存档与权威状态、碰撞、天气和视觉识别必须保持。

复杂改造前先确定第一批范围；不建议当前直接更换引擎、重写渲染器或批量降低所有模型精度。

官方参考：Three.js 的对象优化说明指出场景节点数量也会增加遍历成本，合批需要结合场景结构处理：https://threejs.org/manual/pages/optimize-lots-of-objects.html 。本审计的具体问题来自项目代码，而不是通用网页性能清单。
