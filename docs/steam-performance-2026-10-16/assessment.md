# Steam 多游戏框架：性能实测与技术选择

日期：2026-10-16。此次完成性能评估和方案设计，没有修改游戏实现、原有玩家存档或启动中的原有服务。

## 推荐决策

在后续产品仍以带 NPC、世界模拟和实时 3D 场景的 Steam 桌面游戏为主这一假设下，长期主线推荐 **Unity 6 的受支持稳定版本 + URP + 独立于引擎的 C# 游戏核心 + 独立 AI 推理服务**。

这是一项面向多游戏开发、内容生产和桌面交付的工程选择，不是本次已经实测“Unity 比 Three.js 快多少”的结论。本机未进行 Unity/Godot 同场景原生构建对照，因此全面迁移须经过小型原生样板验收。当前 Three.js 版本保留为可玩的规则参考与迁移回退版本。

不建议把当前 React/Three.js 场景继续扩大为自研通用 3D 引擎；也不建议把全部 TypeScript 业务一次重写。先验证渲染与交付，再逐模块迁移。

## 本次测试条件与边界

- CPU：Intel Core Ultra 7 155H；GPU：Intel Arc 核显；物理内存约 31.4 GiB。
- Playwright Chromium，headless，ANGLE Direct3D 11。通过 WebGL 调试信息确认使用 Intel Arc 硬件，不使用 SwiftShader。桌面浏览器前台、独显、其他驱动和 Steam 客户端尚未验收。
- 生产构建 `npm run build` 成功；窗口 1920×1080、DPR 1、正常动画。
- 固定预览：种子 17，9 名 NPC，世界状态与位置冻结，暴雨/晴天由按钮切换；自动画质调整在诊断构建中禁用；各对比通常预热 4.5 秒、取样 12 秒。
- 冻结状态也会使表现时间在权威时间后 0.35 秒封顶，因此固定预览只能隔离静态场景负载，不能替代持续运行的游戏。
- 真实主页：单独的测试浏览器身份、端口 4174/18082、独立 SQLite 数据库，保留真实状态推进、UI、轮询、角色与天气。测试服务社会模型设置为离线；不代表已覆盖持续 LLM 推理并发负载。
- 真实主页允许原有自动画质策略运行，所以“1080p 窗口”不等于“1080p 渲染缓冲区”。上帝/领主视角取样发生于不同时刻，天气和视野不同，不能当作严格视角 A/B。
- 此次没有修改画质实现来优化游戏。隐藏对象、停绘、关阴影均只发生于诊断构建，属于归因实验，不是可交付的修复。

真实主页第一轮一次 D 键测试：从自动化开始观测至页面领主坐标变化约 **375.8ms**，坐标确实发生变化。此值包含自动化调度与权威状态发布，并非经过高速摄像测得的纯物理按键到显示延迟；单次样本不构成延迟分布。

长预热轮次的同类单次观测约 **861.7ms**，捕获到2次世界接口HTTP 409。页面截图和世界频道还显示“世界修订已变化”的存档连接异常，说明实际控制链路包含修订冲突/重连问题；不能把这两个延迟样本全部归因于帧率或输入续发间隔。此问题已记录，本次未修复。

原始证据：`results.json`、`followup-results.json`、`real-page.json`；截图保存在同目录。真实主页长预热复测另存 `real-page-sustained.json`。

## 可以确认的性能问题

1. **当前问题不能归结为浏览器性能上限。** 同一完整固定场景预热后可以接近 60 FPS；持续游戏则明显更差。加载/预热、动态更新和真实 UI/状态链路必须分别处理。
2. **天气的 CPU 成本值得优先处理。** 真实主页有雨时，已有分段采样中天气更新中位数约 6.4ms、P95 约 16.2ms；固定暴雨领主样本中位数约 10.6ms。采样是有历史混合的滚动窗口，不能当作每个 12 秒区间独立统计，但足以定位高成本路径。`weather.ts` 每帧处理雨滴、水花、屋顶相交及地面高度，源码与计时吻合。
3. **渲染提交与资源负载明显。** 固定场景末帧约 599–830 次绘制调用、316–446 万三角形，阴影帧会改变统计；真实主页上帝样本末帧约 720 次调用、332 万三角形。这里是 Three.js 当次渲染统计，包含相关 pass，不能等同于唯一模型面数。没有 GPU 时间查询，`renderSubmit` 包含 CPU/驱动提交或等待，不能直接标记为 GPU 耗时。
4. **仅降低分辨率不足以稳定改善动态游戏。** 真实主页上帝样本已经降至 1162×654，平均仍约 23 FPS。说明需要同时处理 CPU/更新/提交；不能仅靠继续模糊画面。
5. **操作链路不适合作为通用实时角色控制默认方案。** 输入续发约 200ms，完整世界快照轮询约 250ms，权威固定世界步长 100ms。实际感受取决于输入即时发送、请求返回和表现插值，不能简单把三者相加，但有必要拆分控制、状态发布和视觉更新。
6. **复用边界尚不完整。** `npc-core`、`world-core` 已独立于 Three.js/React；但 `scripts/world/runtime.ts` 和 `src/integrations/world/types.ts` 直接引用营地模拟、`GameState`、社会系统与玩法动作。复制这些文件并不等于获得新的通用游戏框架。

真实主页第一轮捕获 221 条世界响应，解码后平均约 118KB、最大约 161KB；包含启动空响应和操作响应。它证明全量快照传输量会增长，但此次未单独测量 JSON 解析/结构共享成本，不能据此声称它就是最大瓶颈。

长预热轮次捕获241条世界响应，平均约183KB、最大约284KB；同样包含启动和操作响应。持续游戏P95帧间隔约50ms，明显未达到60FPS稳定性目标，且发生于约654p的渲染缓冲区，不能解释为仅首次加载慢。

## 技术路线比较

| 路线 | 对本项目的价值 | 主要成本与边界 | 决策 |
| --- | --- | --- | --- |
| Three.js + Electron | 最大化保留 TS/React，最快形成桌面包 | 浏览器渲染、资源管线和游戏系统优化仍需自建 | 短期交付备选 |
| Three.js + WebGPU | 可探索现代渲染后端和计算能力 | 不能消除世界更新成本，现有 shader/material 需验证 | 不作为第一优先级 |
| Godot 4 原生 | 开源、原生场景工具，适合风格化中小型游戏 | 客户端和部分核心仍需迁移；复杂 3D 工具链按项目验证 | 有效替代方案 |
| Unity 6 + URP 原生 | 适合把资源导入、动画、相机、物理、性能分析与构建流程纳入统一工程 | C# 迁移、材质/动画重建、编辑器与依赖维护、许可成本 | 长期推荐候选，须样板验证 |
| Unreal | 适合高画质大型 3D 方向 | 当前营地项目与复用目标尚不足以抵偿复杂度 | 本阶段不采用 |

不把“是否支持 Steam”作为三者性能排名依据；Steam 接入仍需各自完成初始化、身份、输入、存档和发布验收。

## 推荐的复用架构

```text
游戏 A / 游戏 B / 游戏 C：玩法规则、内容数据、UI、关卡与资源
                       ↓
可复用运行时：时钟、命令/事件、存档迁移、NPC心智、行为调度、世界分区
                       ↓
引擎适配：Unity场景/角色/相机/声音/输入/物理与表现
平台适配：Steam身份/成就/云存档/控制器、文件系统、生命周期
AI适配：原生本地模型 / 可选远程模型 / 确定性降级
```

- 通用领域核心使用普通 C# 数据与接口，不依赖 `UnityEngine`；通用不等于第一天做支持所有类型游戏的大框架。先让第二个小型玩法模块接入，验证边界。
- 各游戏拥有独立规则、配置、存档类型和资产清单；营地的食物、营火、寨门、固定九人名单不进入通用核心。
- 渲染持续更新；移动/碰撞采用适当固定步长；世界经济、NPC思考、感知和UI按各自频率或事件更新。所有模拟使用同一权威时间来源。
- 游戏状态由一个权威核心提交。AI返回意图/结构化建议，经过宿主校验后变成命令；推理超时或崩溃不阻塞世界、输入和渲染。
- 原生推理放独立进程，统一请求队列、并发数、取消、超时、预算、缓存、日志和降级，避免与画面无限争抢 GPU/CPU。
- 单机最终采用进程内状态发布，热路径不再用完整 JSON 快照轮询；若保留跨进程模拟，使用版本化消息、差量状态和有界队列。移动显示采用插值；本地预测必须遵循权威碰撞与校正规则。
- 不同时重写两个长期权威核心。过渡期由现有 TS 服务权威运行，Unity只消费；C#模块通过固定种子/事件回放/存档迁移验证后，再明确切换权威。

## 资源与 Steam 交付

- 为资产建立离线处理：模型减面、LOD、材质整理、纹理压缩、静态碰撞代理、分区与预加载。运行时加载后再做减面不应成为正式版本的主要资源生产流程。
- 草木按空间分区实例化并使用远景替代；阴影区分静态、近景动态与远景简化。保留雨天效果，降低屋顶/地面查询频率并缓存接触数据，粒子运动交给适合的 GPU/批量路径。
- 每款游戏明确自己的三角形、绘制调用、纹理/显存、加载与每帧CPU预算，预算通过目标设备测量确定；不能只规定一个通用模型面数。
- Steam适配独立封装：身份和离线档案、存档槽、成就、Steam Input、启动/退出与崩溃恢复。
- SQLite和设置移入用户数据目录，不用浏览器Cookie当正式存档身份。云同步使用一致性导出/检查点，避免对运行中的 WAL 数据库做不一致文件同步；凭据、模型缓存不混入云存档。
- 退出后继续推进与离线补算是游戏策略，不由窗口意外关闭决定。当前持续世界语义需要明确迁移保留方案；桌面服务有可追踪生命周期，不能遗留无人管理的服务。
- Windows先验收。Linux/Steam Deck性能、手柄导航、休眠恢复和推理后端需单独测试，不凭Windows通过宣称兼容。

## 实施顺序与决策门槛

1. **保留参照与修复高成本路径。** 保存现有基线；处理天气接触查询、森林/阴影预算、预热尖峰、分辨率策略和控制链路，包括本次观察到的409修订冲突。命令的幂等、修订校验和重试要保证不会重复执行；不能通过取消一致性校验解决卡顿。成果必须用真实主页与实际玩法验证，不以固定预览60FPS代替。
2. **创建Unity原生垂直样板。** 复用同一地形、房屋、九名角色、上帝/领主相机、天气，加入行走碰撞、一个完整工作行为和一个NPC对话；通过过渡适配器对接现有权威服务。记录资源转换和材质差异，保持可比画质。
3. **在相同硬件上对照原生发布构建。** 对比晴/雨、远/近景、运动、冷启动与至少15分钟持续运行；单独记录无推理/有推理的帧率、最慢帧、内存、输入延迟。编辑器帧率不作上线成绩。
4. **验收再扩大迁移。** 初步目标：该Arc设备1080p中档向稳定60FPS收敛，P95帧间隔≤20ms、P99≤33ms；控制反馈P95目标≤100ms；没有持续>50ms尖峰、碰撞和存档回归。目标是待验证门槛，不是已达成绩。原生样板若不能在相同质量下改善稳定性/开发流程，就不扩大迁移。
5. **提炼复用核心。** 迁移已明确的NPC/时间/存档/事件等模块，完成TS→C#回放兼容；再用第二个不同的小玩法接入，确保不引用营地专用代码。人口容量按产品需求新增压力档位，此次九人测试不证明百人容量。
6. **Steam集成验收。** 干净Windows机器安装运行、没有Node开发环境、离线游玩、云存档冲突、升级旧档、强杀恢复、输入、平台SDK生命周期；上线发布是独立后续步骤。
